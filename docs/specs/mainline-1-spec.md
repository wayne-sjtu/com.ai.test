# Spec：主线一 —— 客户与渠道服务

## 问题陈述

银行零售财富客户需要通过统一平台完成理财产品（本行自营 + 外部机构代销）的浏览、申购、赎回与持仓管理。当前仓库仅有前后端骨架，没有任何业务能力。参赛要求在 48 小时内交付：主线一全部 17 个功能，以及一条端到端核心交易主链路（客户准入 → 产品浏览 → 适当性校验 → 申购 → 资金处理 → TA 交易确认 → 持仓更新 → 赎回 → 资金回款），且用户侧与管理侧均可查看业务状态和结果。

## 解决方案

在现有 Spring Boot 3 + React 19 单体工程上构建平台：C 端与管理端同工程双路由分区；MySQL 8 存储；本行 TA 与外部 TA 以两个独立 Mock 容器提供真实 HTTP 边界（外部 TA 带故障注入开关）；自营与代销在展示、订单、份额、资金链路上全程可识别、可追溯；任一身份/账户/测评/签署节点失败即终止交易。

## 用户故事

### 接入与身份（功能 1-3）

1. 作为客户，我想通过 PC Web 访问平台，以便浏览和购买理财产品。
2. 作为管理端运营人员，我想登记和维护渠道信息（类型、核心/非核心、状态），以便实现渠道差异化管理。
3. 作为客户，我想用手机号+密码登录 C 端，以便获得受保护的个性化服务。
4. 作为管理端用户，我想用独立账号登录管理端，以便与客户身份严格隔离。
5. 作为客户，我想完成实名认证（Mock 人脸+活体），以便满足开户监管要求。
6. 作为管理端运营人员，我想查看和维护客户尽调信息（身份有效期、反洗钱尽调记录），以便履行尽职调查义务。

### 账户与准入（功能 4-6）

7. 作为客户，我想签约理财账户并分别开通自营/代销交易权限，以便购买对应属性的产品。
8. 作为客户，当我存在持仓、在途交易或未结清费用时，我想被明确告知禁止解约的具体原因，以便理解账户状态。
9. 作为客户，我想完成风险测评并获得 C1-C5 等级，以便系统为我匹配适当的产品。
10. 作为客户，当我的测评到期后，我想在交易时被强制引导重测，以便持续满足适当性要求。
11. 作为管理端运营人员，我想查看客户全部历史测评记录（append-only），以便审计合规留痕且确认记录不可篡改。
12. 作为客户，我想电子签收投资者权益须知、风险告知书、产品协议和代销风险揭示文件，以便完成适当性档案。

### 产品货架（功能 7-9）

13. 作为客户，我想在统一货架看到自营与代销产品，且每只产品强制标注发行方与自营/代销属性，以便明确区分两类产品。
14. 作为客户，代销产品展示时我想看到代销风险提示，以避免两类产品混同误导。
15. 作为客户，我想按品类、期限、风险等级、起购金额、业绩比较基准、发行方及自营/代销标签筛选、搜索和对比产品。
16. 作为客户，我想查看产品要素、说明书、风险揭示书、费率、净值走势和公告。
17. 作为客户，代销产品的净值与公告我想看到外部来源与同步时间标注，以便知悉数据以外部 TA 为准。

### 交易（功能 10-12）

18. 作为客户，我想提交申购并经过金额、额度、交易时段、适当性、费用校验后路由至对应 TA，以便完成购买。
19. 作为客户，当我的风险等级与产品不匹配时，我想收到风险提示并被要求二次确认（或被拦截），以便合规地自主决策。
20. 作为客户，我想提交赎回并经过份额、费用、交易时间校验后路由至对应 TA，以便取回资金。
21. 作为客户，我想在可撤时段内撤销在途交易，以便撤销误操作。
22. 作为客户，我想创建预约申购和定投计划，以便到期自动下单。
23. 作为客户，我想设置现金分红或红利再投资，以便控制分红方式。
24. 作为客户，购买代销 R4/R5 产品时，我想被要求先完成双录（Mock 上传），以便满足高风险产品销售合规要求。

### 持仓与服务（功能 13-17）

25. 作为客户，我想在统一持仓视图看到自营与代销持仓、市值、交易状态和在途资产，且两类资产清晰区分。
26. 作为客户，我想看到每笔持仓的产品市值、浮动盈亏、累计收益，且自营/代销口径一致、来源可追溯。
27. 作为客户，我想查询并导出多品类交易流水，且自营/代销分开归档。
28. 作为客户，我想收到净值、成交、到期和公告消息提醒。
29. 作为客户，我想提交咨询和投诉工单；自营工单内部流转，代销投诉同步发行机构并跟踪闭环。
30. 作为客户，我想使用投教专区的 AI 问答，答案带来源提示、风险声明，且可转人工。
31. 作为管理端客服人员，我想受理和处置客户工单，以便完成服务闭环。

### 管理侧支撑（主线一强依赖的最小管理能力）

32. 作为管理端运营人员，我想查询统一订单列表并查看订单全生命周期状态与路由链路（本行 TA/外部 TA），以便跟踪交易。
33. 作为管理端运营人员，我想发布自营产品净值，以便 C 端估值有数据来源。
34. 作为管理端运营人员，我想通过健康检查页面看到 DB、本行 TA、外部 TA 的组件状态，以便掌握系统运行状况。

### 端到端主链路（赛题硬性底线）

35. 作为评审，我想用种子客户账号从登录开始依序完成：准入校验 → 浏览货架 → 适当性校验 → 申购（资金冻结/扣划）→ TA 确认 → 持仓更新 → 赎回（份额扣减）→ 资金回款，全程在用户侧看到状态流转，在管理侧看到订单与链路。
36. 作为评审，我想演示巨额赎回场景：单日赎回超产品阈值时超限部分延期确认。
37. 作为评审，我想通过外部 TA 故障注入开关演示通信超时、结果未知、重复回调场景下系统保持一致。

## 实现决策

### 架构与基座

- 就地在现有工程生长；C 端与管理端为同一 React 工程内两个路由分区，各自布局壳。
- 数据库 MySQL 8（ADR-0007）；Docker-Compose 一键部署（主系统 + MySQL + 本行 TA Mock + 外部 TA Mock 四容器）。
- 渠道数据驱动：渠道表（渠道码、类型、核心/非核心、状态），C 端请求携带渠道码；仅 PC Web 真实实现，其余渠道 Mock 登记。
- 统一认证：服务端 Session（内存存储），客户/管理端两套登录端点，session 属性标记身份类型，越权访问在拦截层拒绝（ADR-0003、ADR-0004）。
- 适当性引擎为独立 service：输入客户 C 等级+测评有效期+产品 R 等级+客户范围，输出 通过/二次确认/拦截 + 留痕；C×R 动作映射数据驱动。

### 领域模型

- 客户聚合与理财账户：单一理财账户（签约状态机：未签约→已签约→解约）+ 自营/代销两个独立交易权限；解约前置校验（持仓/在途/未结清费用 → 拒绝并返回原因列表）。
- 风险测评：append-only 快照表（答案、得分、C 等级、有效期起止），应用层禁 UPDATE/DELETE；有效期 1 年，到期交易前置校验拦截并引导重测。
- 订单：单一订单表 + product_type（自营/代销）区分，隔离靠类型字段 + 各自状态机 + 订单事件轨迹表（记录每步路由/确认事件，含 TA 标识与报文流水号）。
- 状态机（来自拷问共识，精确编码如下）：

```
申购: CREATED → SUBMITTED → TA_ACCEPTED → CONFIRMED → SETTLED(终态)
赎回: CREATED → SUBMITTED → TA_ACCEPTED → CONFIRMED → REDEEMED(终态)
异常终态: CANCELLED(撤单) / FAILED(校验失败、TA拒绝) / EXPIRED(预约作废)
特殊: PENDING_QUEUE(巨额赎回延期确认) → CONFIRMED
预留: REVERSED(冲正，本阶段仅枚举不实现)
约束: 状态只进不退；每次迁移写一条订单事件
```

- 简化账务（ADR-0006）：资金账户（余额：可用/冻结）+ 资金流水（幂等键 = 订单号+动作类型）+ 份额持仓，三者通过订单号关联、支持三方核对。
- TA 边界：本行 TA Mock（同步确认为主）与外部 TA Mock（异步确认+回调，故障注入开关：正常/超时/拒绝/延迟确认）为两个独立容器（ADR-0005）；银行侧不替代外部 TA 做最终确认。
- 估值：实时计算（份额 × 最新已确认净值），自营/代销同一估值函数，仅来源与时间戳标注不同；日终快照仅用于收益走势历史点。
- 最小双录：交易前校验链中的判定步骤，触发条件 = 代销产品且 R4/R5；双录本体 Mock 为标志文件上传，未完成则拦截交易。
- 巨额赎回：产品级阈值（默认 10%），单日赎回超限时超限部分进 PENDING_QUEUE 延期确认（T+1 顺延）。
- 申购校验最小集：产品总额度（占用/释放，在途订单占额度）+ 产品级交易时段 + 起购金额 + 固定申购/赎回费率。
- 功能 12 分级：撤单（状态机）+ 分红方式设置（走 TA 报文）真实实现；预约申购/定投 = 计划表 + @Scheduled 周期扫描到期触发下单；到期滚存按产品规则处理。
- AI 投教问答：LLM 优先 + FAQ 关键词降级；答案强制带来源提示、风险声明、人工转接入口；敏感问题转人工并保留问答记录。
- 消息提醒：站内信为主（净值、成交、到期、公告、投诉进度），统一消息表。

### 种子数据

- 客户 6 个：C1/C3/C4/C5 各一（覆盖适当性 通过/二次确认/拦截 三分支）+ 测评过期 1 个 + 未签约 1 个。
- 产品 8 只：自营 R1/R3/R4/R5 + 代销 R2/R3/R4/R5，覆盖不同期限、起购、费率、开放状态。
- 每只产品 30 个交易日净值历史；部分客户带存量持仓与在途订单；管理端运营/客服账号各 1。

### 运维与交付

- 健康检查双端点：Actuator /actuator/health（Compose healthcheck 引用）+ 自定义组件矩阵端点（DB/本行 TA/外部 TA 状态）。
- 交付文档结构：docs/ 下 requirements / design / manual / test-report / process / decisions / reference / specs。

## 测试决策

- **唯一主 seam：后端 HTTP API 边界**。集成测试用 @SpringBootTest + MockMvc/TestRestTemplate 走真实 REST 端点（含 Session 认证），只断言外部可观察行为（响应体、状态码、订单状态、资金流水、持仓变化），不断言内部实现细节。
- TA 边界在 seam 内打桩：MockWebServer 挂在 HTTP client 层，覆盖正常受理/超时/拒绝/延迟确认/重复回调（差错矩阵场景）。
- 数据库：Testcontainers MySQL 8，与生产同源，避免方言差异。
- 好测试标准：改内部实现不破坏测试；每个异常场景（重复提交、额度不足、适当性拦截、双录缺失、巨额赎回、TA 超时）至少一条用例。
- 前端不设自动化 seam：lint + build + 手动验证（沿用既有决策）。
- 无先例可循（绿地），本 spec 的测试将是仓库第一批测试；verify.sh 作为统一执行入口。

## 范围外

- 主线二/三/四的完整实现，仅做主线一强依赖的最小部分（产品/净值种子数据、统一订单查询、健康检查）。

- 完整双录（视频存储、完整性校验、调阅）——仅判定+Mock 标志文件。

- 客户 360、AI 标签分层、智能推荐、佣金结算（主线二）。
- 客户单日/单笔限额、阶梯赎回费率。
- H5/App/小程序渠道的真实实现；前端自动化测试框架；多实例水平扩展（内存 Session 的显式取舍）。
- 统一 API 网关、消息推送网关（短信/App 推送）——站内信已满足功能 15。
